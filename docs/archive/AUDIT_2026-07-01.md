## Findings

### C1 — [High→Critical · VERIFIED] Booking-submission transaction is a no-op; rollback never fires
`novoton_holidays/src/Services/BookingSubmissionService.php:128-208` + `src/Repository/BookingRepository.php:217/242/312`
`submitOrder()` opens `START TRANSACTION` (128) then, per room-group, calls `recordBuilder->persist()` → `BookingRepository::create()`/`update()`, **each of which opens its own `START TRANSACTION`/`COMMIT`** (217/225, 242/251). MySQL has no nested transactions: the inner `START` **implicitly commits** the outer one, and the inner `COMMIT` closes it. So when a later group's API call throws, the `ROLLBACK` at 198/218/235 runs with **no active transaction and undoes nothing** — earlier groups' bookings stay committed. The intended all-or-nothing multi-room submission does not exist; the rollback (and its explanatory comment at :200) is dead code.
*Failure scenario:* 2-room order, group 1 books + reserves, group 2's Novoton call fails → DB keeps a confirmed group-1 booking + `travel_bookings` mirror alongside a failed group-2 record, with no atomic unwind. Financial exposure if payment is captured for the whole order.
*Fix:* Repositories must not open their own transaction when callable inside one — remove the inner `START/COMMIT` and let the caller own it, or adopt Sphinx's `withTransaction()` nesting-aware helper. Then restructure `submitOrder` to **persist+COMMIT the booking, call the API OUTSIDE any transaction, then record the response in a separate short transaction** (this also prevents holding row locks across the network call once nesting is fixed). Unblocks C1-related test gaps (H5).

> **✅ FIXED 2026-07-01** — `BookingRepository::create/update/delete` now route through a nesting-aware `withTransaction()` (only the outermost call issues START/COMMIT, so an inner write can never implicitly commit a caller's transaction). `submitOrder`'s outer transaction + dead ROLLBACKs were removed: each group's booking is persisted+committed by `create()`, the API is called **outside** any transaction, and the response is recorded by `update()` in its own short transaction. Regression test `BookingRepositoryTransactionNestingTest` proves inner writes join a single transaction and a nested failure rolls back exactly once. Verified: PHPStan L10 clean, 452 novoton unit tests green, Rector + php-cs-fixer clean.

### H1 — [High · VERIFIED] "Batch" upserts are row-by-row N+1 (sync cron)
`sphinx_holidays/src/Repository/HotelRepository.php:62-157` and `DestinationRepository.php:43-77`
Despite the name, `upsertBatch()` loops one `INSERT … ON DUPLICATE KEY UPDATE` per row (confirmed: `foreach` at :62, query at :68). 100k hotels → 100k round-trips; the stream-and-chunk design upstream is defeated.
*Fix:* true multi-row `INSERT … VALUES (…),(…) ON DUPLICATE KEY UPDATE col=VALUES(col)` (the `IF(...)` update clauses work with multi-row VALUES).

> **✅ FIXED 2026-07-01** — both `upsertBatch()` methods now build one multi-row `INSERT … ON DUPLICATE KEY UPDATE` per chunk (hotels: 100 rows/statement matching the sync batch size; destinations: 500 rows/statement), passing a flat placeholder param list to a single `db_query`. 100k hotels: ~100k round-trips → ~1k. Guarded by 5 new tests in `UpsertBatchTest` (one statement per chunk, per-row param layout, invalid-row skipping, chunking).
>
> **✅ MARIADB PORT + LATENT BUG FIX 2026-07-03** — all 8 upsert sites repo-wide (both sphinx repos + `SphinxCacheRepository` + 4 novoton sync sites) converted from the MySQL-8-only `AS new_row` alias to the portable `VALUES(col)` form — the addons now run on **MySQL 8.0+ and MariaDB 10.6+**. Executing the real repository upserts against MariaDB 10.11 exposed a **pre-existing correctness bug affecting MySQL too**: `ON DUPLICATE KEY UPDATE` assignments evaluate left-to-right, and the `IF()` change-detection clauses sat *after* the plain column assignments — so they always compared new-vs-new and **`product_needs_update` / `product_skip_reason` never fired** (product content never refreshed on hotel changes). The detection clauses now run FIRST, and an engine-level proof verifies insert, duplicate-update, needs-update flip, and skip-reason clearing on MariaDB.

### H3 — [High · VERIFIED] `ON DELETE RESTRICT` FK makes booked hotels undeletable
`novoton_holidays/functions/install.php:578-593` (`fk_nb_hotel_id`, `fk_nar_hotel_id`)
Bookings/alt-requests reference `novoton_hotels` with RESTRICT, so `HotelRepository::delete()`'s final `DELETE FROM novoton_hotels` throws whenever history exists → the whole delete transaction rolls back and the hotel can never be removed or re-synced (delete-then-reinsert reconciliation breaks). This is the same constraint behind the earlier bulk-delete workaround.
*Fix:* bookings are historical and must outlive the master row — change to `ON DELETE SET NULL` (nullable `hotel_id`) or drop the FK and keep `hotel_id` as a denormalized snapshot (the booking already stores name/dates/prices).

> **✅ FIXED 2026-07-01** — chose **drop-the-FK** over `SET NULL`: `hotel_id` is the stable Novoton `IdHotel`, so keeping the value restores the join automatically when a hotel is re-synced (SET NULL would sever it permanently). `install.php` no longer creates the two RESTRICT FKs and `fn_novoton_holidays_setup_db()` now drops them idempotently on existing installs (checked execution + `fn_log_event`, no `@`-suppression). Both tables keep their explicit `hotel_id` indexes and denormalized display fields; the only bookings→hotels read joins via LEFT JOIN (`BookingQueryService.php:121`), so deleted-hotel bookings still display.

### H4 — [High · VERIFIED (with nuance)] Provider FK asymmetry / inconsistent integrity model
`novoton` installs 5 FKs (`fn_novoton_holidays_setup_db`); **`sphinx` installs none** and instead relies on a `CleanupCommand` cron to unlink orphaned `product_id` refs. Two different integrity philosophies across sibling providers; sphinx's destination→hotel and whitelist relationships have neither FK nor guaranteed cleanup.
*Fix:* pick one model — either add sphinx FKs (at minimum `sphinx_destination_whitelist.destination_id → sphinx_destinations`) or explicitly document the cleanup-cron as the design and ensure it covers every relationship, not just products.

> **✅ DECIDED & DOCUMENTED 2026-07-01** — standardized on: *CASCADE FKs only for true child data; no FKs for historical/cross-aggregate references (hooks + cleanup crons keep them consistent)*. Recorded as §16 of `Documentation/shared-travel-core-architecture.md`. Deliberately did **not** add the whitelist FK or auto-cleanup: the whitelist is admin configuration and must survive destination re-imports — auto-deleting "orphans" mid-re-sync would destroy admin config. Sphinx's `CleanupCommand` already covers the relationships that need repair (orphan bookings, product links).

### H5 — [High · Agent-reported] Critical write paths untested; integration harness structurally can't test writes

I.e. the C1 nesting defect is *why* the write paths are untestable.

### M1 — [Medium · Agent-reported] `@`-suppressed, non-atomic schema migrations
`novoton_holidays/functions/install.php:529-550` runs a 7-step `TIMESTAMP→INT` migration on `novoton_cache` as separate `@db_query()` calls with no per-step guard; a mid-way failure (e.g. `DROP` succeeds, `CHANGE` fails) leaves the table broken and **silent** (errors suppressed). ## Deep-pass addendum — pricing correctness & duplication map (direct, 2026-07-01)

### Pricing / currency — money path is SOUND (verified)
`add_to_cart.php:660` stores the **converted primary-currency** price in `product['price']` (`convertFromApiCurrency($total_price, $primaryCurrency)`) but keeps the **raw EUR** price in `extra['total_price']`; `PreOrderPriceVerifier` compares `extra['total_price']` (EUR) to the live API price (EUR) — apples-to-apples, no currency mismatch. `CurrencyService::convertFromApiCurrency` uses correct coefficient math (`round(apiPrice / sourceCoeff * targetCoeff, 2)`). No critical pricing bug found.
- **P1 — [Low] Currency-mismatch fallback in `PreOrderPriceVerifier.php:89`.** When `extra['total_price']` is absent it falls back to `$product['price']` (store/primary currency, e.g. RON) and compares that to the EUR API price. `total_price` is normally always set, but a stripped/legacy cart item would be mis-corrected (RON-vs-EUR → bogus "far above API" or a wrong upward correction). *Fix:* if `extra['total_price']` is missing, skip the item (or convert back to API currency) instead of comparing mismatched currencies.
- **P2 — [Info/design] Price decreases never correct the cart down.** Only Case 1 (form < API) corrects, upward. If the live price drops before checkout the customer keeps paying the higher cart price (a "price dropped" alert shows, no correction). Deliberate merchant-favoring "never block, correct up only" policy — confirm it matches the intended "No Surprises" UX.

> **✅ CHECKOUT GUARD UNIFIED 2026-07-04 (maintainer-approved best-practice pass, items 1–3):** both providers now share ONE settings-backed policy via `TravelCore\Services\CheckoutPriceGuard` — (3) match epsilon €0.01 everywhere (novoton previously had none → sub-cent float noise triggered corrections); (2) alert thresholds are configuration with an absolute floor: `checkout_alert_percent` 20 (replaces novoton's 55%-of-API setting and sphinx's hardcoded 20%-of-form; percent base standardized to API) + `checkout_alert_floor` €5 + `checkout_big_overage` €100; (1) **disclose-and-reconfirm on increases** (EU CRD): a correction beyond `checkout_absorb_increase` (default €0) updates the cart, notifies the customer, and **blocks the order click** (`$allow = false`) so they re-confirm the new total — sphinx previously corrected silently, novoton corrected-with-notification but charged on the same click. Increases within the allowance are absorbed by the merchant at the shown price. Novoton's `price_higher_threshold` setting is superseded/ignored. Covered by `CheckoutPriceGuardTest` (defaults/overrides/epsilon) + 6 new unified-config policy cases. P1 (missing-`total_price` fallback) and P2 (no correct-down) remain open by design.
